## D001 — 课件总页数固定为常量，不做成数据

- **日期**：2026-09-18
- **背景**：打卡"未讲完"时原本需要手填"当前页/总页"两个数字。老师反馈总页数没必要每次填。
- **问题**：totalPage 从哪里来、存哪里？
- **方案**：
  - A. 保持手填（现状）
  - B. 固定写入 `constants.js`，UI 只读展示 ✅ 选择
  - C. 新建云集合存课件元数据
- **选择**：B。`pptTotalPages` 数组与 `pptList` 按下标一一对应（23 项），值来自 PPT 文件实测。注意：该数组**定义在 `constants.js` 模块内但不导出**，外部只能通过 `pptList[i].totalPage` 读取 —— "没导出"不等于"不存在"，核对时别只看 `module.exports`。
- **为什么**：总页数是课件的固有属性，一学期内不变。单用户、23 个课件，常量是最小解。
- **为什么拒绝 A**：重复劳动 + 历史数据因此不一致（就是这次要回补的脏数据根源）。
- **为什么拒绝 C**：为 23 个不变的数字建集合 + 维护流程，违反 KISS 和单用户假设。
- **已验证**：23 个值用 PowerShell 解 pptx zip 数 `ppt/slides/slideN.xml` 得到，并 `node -e` 加载核对一致。
- **何时重审**：课件列表动态化（用户自助增删课件）、多老师共用、换学期频繁。

## D002 — 旧数据回补放客户端，不用云函数

- **日期**：2026-09-18
- **背景**：历史 `progress` 记录里 partial 状态的 totalPage 是手填值，可能与固定值不一致，需批量修正。
- **问题**：批量 update 放哪执行？
- **方案**：
  - A. 写一个一次性云函数批量改
  - B. 客户端 `fixLegacyTotalPages()`：分页拉全量 → 逐条 `doc().update()`，storage 标记防重 ✅ 选择
- **为什么**：单用户，所有记录都是同一 openid 创建，集合权限"仅创建者可读写"已足够客户端更新自己的记录；省一次云函数部署；数据量 < 几百条，客户端 100 条/批毫无压力。
- **为什么拒绝 A**：部署链路（上传云函数 + 控制台调用）比重写几行客户端代码重，且一次性任务不值得留云函数。
- **已验证**：代码 `node --check` 通过；**实际执行未验证**（待用户在开发者工具看到控制台 `已回补 totalPage 记录数：N`）。若权限不允许 update，此处会抛错，被 catch 后不影响主流程，届时改用云函数方案。
- **何时重审**：多用户（记录归属分散，客户端改不动别人的记录）、数据量级变化。

## D003 — 调课数据存本地缓存，不进云库 ⚠️ **已废弃（2026-09-23，由 D015 取代）**

> **废弃原因**：本条的前提是"单用户单设备"。实际是两个人在用，课表是**共享事实** —— 她调的调课他看不到，换手机还会丢。2026-09-23 已改为云集合 `schedule` + 当周有效，见 **D015**。以下内容仅作历史记录保留。
> 另注：本条原文写的 `{"周-节次": ...}` 含义含糊（会被读成"周次-节次"），实际代码里是**星期几-节次**（`1-5` 是周一到周五，来自 `new Date().getDay()`）。且它**永不重置**，一次调课会永久生效。

- **日期**：项目早期（2026-09-18 确认延续）
- **背景**：课表页支持点课程卡片调班/取消课。
- **问题**：调课覆盖存哪？
- **方案**：
  - A. 云库存调课记录
  - B. 本地 `wx.setStorageSync('customSchedule', {"周-节次": 班级id|"none"})` ✅ 选择
- **为什么**：调课是高频微调（今天这节课换班/取消），单设备使用，本地写入零延迟、零配额、零同步逻辑。
- **为什么拒绝 A**：单用户单设备下云库只增加延迟和复杂度。
- **已验证**：课表页 renderSchedule 用 initialSchedule + customSchedule 覆盖渲染，用户日常使用中。
- **何时重审**：换手机/多设备需要课表同步（那时必须上云，且要设计冲突规则）。
- **注意**：清小程序缓存 = 丢失所有调课记录，此风险已接受。

## D004 — 课表页滚动残留用 onShow + pageScrollTo 修复

- **日期**：2026-09-18
- **背景**：课表页下滑后切到打卡 tab 再切回，页面停在原滚动位置，sticky 的周条（周一~五）与时间轴内容重叠。
- **问题**：如何让切回时归零？
- **方案**：
  - A. onShow 里 `wx.pageScrollTo({scrollTop: 0, duration: 0})` ✅ 选择
  - B. 去掉 sticky，改普通布局
  - C. 换成 scroll-view 自己管 scrollTop
- **为什么**：一行调用，不改布局、不改变交互（页内滚动保留，只在跨 tab 回页时归零），符合用户诉求"切回来自动刷新回没拖过的情况"。
- **为什么拒绝 B**：sticky 周条是设计的一部分（滚动时快速切周），去掉是功能退化。
- **为什么拒绝 C**：scroll-view 需要定高，tab 页用页面滚动更简单，改造面大。
- **已验证**：语法过；UI 行为待开发者工具确认。
- **何时重审**：若 pageScrollTo 在某些基础库版本有回弹/不生效，再评估 C。

## D005 — input 与 view 的居中样式分离

- **日期**：2026-09-18
- **背景**：总页展示值改成 `<view class="glass-input">` 后，文字水平居中但垂直贴顶。
- **问题**：如何垂直居中且不伤到真正的 `<input>`？
- **方案**：

- **何时重审**：无（除非发现 view 上 flex 也有兼容问题）。

## D006 — 业务逻辑全部客户端直连云库，不部署业务云函数

- **日期**：2026-09-18（确认现有事实）
- **背景**：仓库里 `cloudfunctions/quickstartFunctions` 是 CloudBase 模板自带的演示代码（sales 集合 CRUD、getOpenId 等）。
- **决策**：当前所有业务（打卡、查询、回补）都走小程序端 `wx.cloud.database()` 直连；**不依赖、不部署**该模板云函数；新增业务逻辑默认也不走云函数。
- **为什么**：单用户 + 数据量极小 + 无跨用户鉴权需求，客户端直连最简单；模板云函数里的 sales 逻辑与本项目无关，留着不碍事但绝不能被误当业务代码调用。
- **何时重审**：需要聚合统计超客户端配额、多用户权限、定时任务时，引入业务云函数。

## D007 — 智能推荐算法：按"当前时间已过最近一节化学课"推班

- **日期**：项目早期（2026-09-18 确认延续）
- **背景**：打卡首页要自动猜"老师现在最可能给哪个班打卡"。
- **规则**：遍历 timeSlots，找今天 `currentMins >= slotStart` 的最后一个有课的 slot → 其班级为推荐；标签按 上课中 / 刚下课(≤30min) / 上节课 区分；今天无已上课则找明天第一个有课 slot 标"下节课"。
- **为什么**：不引入任何学习逻辑，纯时刻表推导，KISS 且符合老师"刚下课就打卡"的真实场景。
- **已知边界（接受）**：`tomorrow = (currentWeek % 7) + 1` 在周末/跨月场景下未专门验证；只覆盖化学课，其他科目课程不在 initialSchedule 里。
- **何时重审**：排课规则变化（如走班制）、或推荐准确率被老师抱怨时。

## D008 — 概览页用"排名式进度对比"，并固定颜色分工

- **日期**：2026-09-18
- **背景**：概览页原为 2x2 卡片，只显示每班最新课件名 + 状态。问题：课件名换行导致点/文字错位；看不出各班进度差异，无法回答"该催哪个班"。
- **问题**：怎么让老师一眼看出四班快慢与差距？
- **方案**：
  - A. 保留 2x2 Bento 网格，仅调样式
  - B. 排名式横向卡片列表：按全书进度**升序**（最慢排最前），每卡显示 第 N 讲/23 + 全书百分比 + 细进度条 + 当前课件（单行省略） + 状态 + 与榜首差距 ✅ 选择
  - C. 四班横向柱状图 / 环形图
- **为什么选 B**：升序=最需加快的班永远在第一屏第一张，直接对应老师诉求"我需要加快哪个班"；卡片承载的信息量（讲次、页数、日期、差距）比纯图表多；单列布局在窄屏上比 2x2 更好读。
- **为什么拒绝 A**：换行错位与"看不出快慢"都不是样式层能解决的，需要信息结构变化。
- **为什么拒绝 C**：四种颜色区分班级会与状态色语义冲突，且窄屏横向柱状图标签必然挤压；dataviz 规范也要求"身份靠标签而非颜色"。
- **颜色分工（后续改动必须遵守）**：靛蓝 `#502BD8` **只用于进度条填充**（单一量度的量度色）；绿 `#00C48C` / 橙 `#FF7B52` 是**保留状态色**，永远"圆点 + 文字"成对出现，绝不单独用颜色表意；班级身份靠大号文字，不靠颜色；数值/百分比文字用墨色 token，不用量度色。
- **已验证**：`node --check` 过；模拟四班数据（含无记录班级）验证排序、百分比、差距折算全部正确；配色三件套过 dataviz 校验（对比度 WARN 已由可见文字标签抵消）；用户开发者工具目检通过（2026-09-18）。
- **何时重审**：班级数超过 6 个（排名列表过长需换形态）、或需要看趋势（那就该加折线而非改这个列表）。

## D009 — 写权限收敛为 openid 白名单（自定义安全规则）

- **日期**：2026-09-18 **（已决定，未执行）**
- **背景**：小程序原按"单用户假设"设计。用户实为两人使用（本人 + 女友），且计划上线。"单用户假设"在此被打破，但**只破一半**：写方固定为两人，读方可以是任何人。
- **问题**：如何表达"只有两个指定微信号能写，其他用户只读"？
- **方案**：
  - A. 云开发控制台 **自定义安全规则**：`read: true` + `write: auth.openid in [两人 openid]` ✅ 选择
  - B. 所有写操作走云函数，云函数内校验 openid 白名单
  - C. 保持现状（任何用户可创建自己的记录）
- **为什么选 A**：纯控制台配置、**零代码改动**；需求规模只有两个人，不值得为此引入云函数；不触碰 AGENTS.md §4"不新增业务云函数"约束。
- **为什么拒绝 B**：为两条白名单引入云函数是过度设计（违反 KISS）。且云函数以 `wx-server-sdk` 管理员身份运行，反而让权限模型变复杂。
- **为什么拒绝 C**：上线后任何陌生人都能往 `progress` 写记录，会直接污染四班进度视图。
- **已知副作用（接受）**：
  1. `read: true` = **任何微信用户**可读全部打卡记录（教学进度，敏感度低，用户明确接受）。
  2. 白名单规则下两人可**互相改写/删除对方的记录**，比"仅创建者可写"更宽 —— 这是**想要的**，顺带解决"老师删不掉污染记录"的问题。
  3. 自定义安全规则**只约束客户端 SDK**；云函数（`wx-server-sdk` 管理员身份）**不受其约束**。将来引入云函数必须重新评估。
  4. openid 硬编码在云端规则里。**openid 绝不可写入本仓库**（仓库已推送至公开 GitHub），女友换微信号需改规则。
- **执行顺序（不可颠倒）**：① 从控制台已有记录取老师 openid → ② 让女友在当前宽松权限下打一条卡，取她的 openid → ③ **然后才**改规则。先改规则就拿不到第二个人的 openid 了。
- **已验证**：**未执行、未验证**。规则表达式 `auth.openid in [...]` 的具体写法**需在控制台规则编辑器实际确认**（不照抄本文档）。
- **何时重审**：引入云函数时、使用成员变化时、需要更细粒度权限（如只读成员、分班隔离）时。

## D010 — 打卡智能推荐排课：时间线分级扫描 + 调课联动

- **日期**：2026-09-20
- **背景**：原智能推荐在周末或非当天课时段存在逻辑 bug（明天下节课使用了当前分钟比较 `currentMins >= slotStart`，导致周日错误推荐周一晚自习 2606 班而非离当前最近的周一第4节 2608 班），且未与调课缓存 `customSchedule` 联动。
- **方案**：
  1. 统一通过 `getScheduleClass(week, slot)` 读取排课，优先使用 `customSchedule` 调课覆盖；
  2. 匹配规则三级分流：
     - ① 当前上课中（`start <= now <= end`）：推荐该班，标签 `上课中`；
     - ② 刚下课 60 分钟内（`0 < now - end <= 60`）：推荐该班，标签 `刚下课`；
     - ③ 非即时打卡窗口：先扫今天剩余尚未开始的 slot，若无则跨天循环扫描未来 7 天，取最早有排课的 slot，推荐该班，标签 `下节课`。
- **为什么**：符合老师课后即时打卡与事前备课/补打卡的第一性原理直觉；100% 覆盖周末、午间、晚间、调课取消与改班等各种边缘场景。
- **已验证**：Node.js 9 个边界测试用例（周日 22:16、周日 09:00、周一早晨、周一课中、周一刚下课、午休后看晚自习、周五下午看下周一、调课改班、调课取消）全部通过。
- **何时重审**：作息时间表变更、排课规则发生本质变化。

## D011 — 课表页与概览页 Single Viewport（一页式）免滑动布局

- **日期**：2026-09-20
- **背景**：老师反馈课表页和概览页原本需要上下滑动浏览，希望无需滚动、一屏全部看完。
- **方案**：
  - 页面级 `height: 100vh; overflow: hidden;`，结合 `display: flex; flex-direction: column;`。
  - 底部通过 `calc(140rpx + env(safe-area-inset-bottom))` 精确避让悬浮 custom-tab-bar。
  - 课表页：移除“化学课”字样，11 个时段通过 `flex: 1` 均分中间高度，有课为微渐变胶囊，无课为极简淡灰虚线框。
  - 概览页：移除“按全书进度排序...”副标题，4 张班级进度卡片通过 `flex: 1` 均分中间高度，微调字阶比例（班级 32rpx，大数 52rpx，进度条 8rpx）。
- **为什么**：高中老师在快节奏课间需要极速获取信息，一屏览尽无认知与操作摩擦；弹性 Flex 布局能自适应各类 iOS/Android 屏幕尺寸。
- **已验证**：语法检查通过，UI 结构无绝对定位，所有文字在容器内安全流式对齐。
- **何时重审**：班级数增加到 5 个以上，或者一日节次增加到 13 节以上导致一屏极度拥挤时。

## D012 — 提交/撤销都过自定义确认弹窗；撤销目标 = "上次记录"徽章那一条

- **日期**：2026-09-23
- **背景**：打卡页原来点"记录进度"一次点击直接写库，误触无法回退；用户明确要求"加弹窗，点确认才执行"。
- **方案**：
  - 不用 `wx.showModal`（系统原生外观固定不可改，与项目设计系统脱节），自绘遮罩 + 卡片，沿用 `--radius-lg`/`--primary-color`/`hover-scale`/`animate-fade-up`。
  - `submitRecord()` 拆成两段：校验 + 开弹窗；真正写库移到 `doSubmit()`。
  - **撤销目标改为"上次记录"徽章显示的那一条**（当前班级 + 当前课件的最近一条），而不是"本次会话刚提交的"。
- **为什么这样定撤销目标**：用户实际诉求是"我上次误点的打卡想删掉"。绑到 `historyState` 后两种场景自然统一 —— 刚提交完徽章就是那条；翻到任意班级+课件也能删它的历史记录。且因此**删掉了 `lastRecord` 与 `showUndo` 两个状态字段**（可用性直接由 `historyState` 推导，少两个需要同步的字段）。
- **已知副作用（接受）**：
  1. 撤销按钮**常驻**，无可撤销记录时置灰（保持同尺寸，避免出现/消失导致布局跳动）。
  2. 弹窗里带**日期**行，避免删错。
  3. 云库预设权限「仅创建者可读写」下，**只能删本机账号自己创建的记录**；删别人的会被服务端拒绝并弹明确提示。跨账号删需等 D009 白名单落地。
- **已验证**：`node --check` 通过；离线状态机测试 45 项（含"点记录进度不写库""连点只写一条""点撤销时还没删""删的是历史记录那条 _id"）全部通过；用户开发者工具验收通过（2026-09-23）。

## D013 — 进度轴：按真实记录点亮，不按位置切片

- **日期**：2026-09-23
- **背景**：进度轴初版用 `index < axisIndex` 判断"已讲过"，隐含"当前进度之前的课件都讲过"。老师会**跳着上课**（跳过 1.2.3 先上 1.3.1），位置切片会把没上过的 1.2.3 也点亮 —— 用户发现并质疑了这一点。
- **方案**：
  - 新增 `fetchClassProgress(classId)`：拉该班**全部**记录，算出 `axisIndex`（实际该讲的一讲）+ `axisDone`（23 项布尔数组，哪些课件`completed`过）。
  - 点亮规则改为 `axisDone[index]`；`partial` 的记录**不算讲过**（只讲一半的课件保持灰，进度也停在原地）。
  - **`axisIndex` 与表单的 `pptIndex` 解耦**：换课件不让进度轴移动，轴只表示该班实际进度。刷新时机只有三个 —— 换班级、提交、撤销，外加每次 `onShow`（从别的页面切回来重新拉最新）。
- **为什么**：跳着上课是真实教学行为（课时被冲掉、先讲后面再回补）。位置切片需要"教学严格顺序"这个不成立的前提。
- **已知副作用（接受）**：
  1. 每次刷新要拉该班全量记录，**必须分页**（小程序端 limit 上限 20，见 AGENTS.md §3）。
  2. 同时这也是"撤销目标"之外唯一需要全量记录的地方；`getLatestPptIndex`（只取最新 1 条）已被本方法取代并删除。
- **已验证**：离线状态机测试覆盖"跳过 1.2.3 时 1.2.3 保持灰""partial 不点亮""23+ 条记录分页取全""onShow 重置进度轴""首次进入不与 smartRecommend 抢"；居中算法独立复算 5 种屏宽 × 23 节点偏差 0.0000px；用户开发者工具验收通过（2026-09-23）。

## D014 — 打卡页一屏布局（space-between 均分）与课表手势方向

- **日期**：2026-09-23
- **背景**：加上进度轴后打卡页会超出一屏，且第一版把进度轴做成 `flex:1` 吸收全部多余空间，结果"上方内容挤在屏幕顶部、下方一大块空白"，用户反馈难看。
- **方案**：
  - 页面锁 `height:100vh; overflow:hidden`，容器 `display:flex; flex-direction:column; justify-content:space-between`（与课表页/概览页同一套做法，见 D011）。
  - 多余空间**均分到三个间隙**（hero↔卡片区、卡片区↔按钮区、按钮区↔进度轴），进度轴因此自然沉到底部栏上方；小屏自动收紧、大屏自动撑开，不需要媒体查询。
  - 同时压缩了 9 处尺寸（卡片内边距 40→28、卡片间距 24→16、提交按钮 112→96、撤销按钮 88→74、问候语 64→56 等），保证最小屏也能放下。
  - **课表左右滑动方向**：**左滑 = 后一天，右滑 = 前一天**（用户从初版"左滑=前一天"的反直觉写法改为符合横向翻页习惯的方向）。到边界（周五左滑 / 周一右滑）播回弹动画，不做静默无反应。
- **为什么**：老师课间需要一屏览尽、零滑动摩擦；空间按屏高自适应比固定尺寸更稳。
- **实现要点**：
  1. 切周动画**必须挂在新加的 `.timeline-wrap` 包裹层上**，不能挂在 `.timeline-box` 上 —— 后者已有 `.animate-fade-up`（含 `opacity:0`），两个 animation 类叠加会让内容卡在透明状态。
  2. 横滑起点落在课程卡片上时，用 `_swipeConsumed` 标记吞掉可能被合成的 `tap`，避免误弹调课面板（微信 tap 的位移阈值官方未公布，做防御性处理）。
  3. 同名动画 class 不会重播，必须 `setData({slideClass:''})` 再 `wx.nextTick` 挂上。
- **已验证**：垂直预算按 5 种机型从 WXSS 实测值复算，全部一屏容纳（最紧的 iPhone SE「未讲完」态余 56rpx）；手势离线测试 16 项（方向、边界、竖滑/斜滑拒绝、tap 冲突、点 pill 与滑动共用同一路径）全部通过；用户开发者工具验收通过（2026-09-23）。

## D015 — 调课覆盖移到云集合 `schedule`，当周自动失效（取代 D003）

- **日期**：2026-09-23
- **背景**：D003 把调课存本地缓存，前提是"单用户单设备"。实际是两个人用，用户发现"她在她手机上点的调课我这里看不到"，并预期"新的一周应该重置"。核对代码后确认两个问题：**本地缓存不共享**，且 key 只有「星期几-节次」没有日期维度，**调课永不失效**（9 月调的一节课 12 月还在生效）。后者还连带影响智能推荐 —— 它读同一份缓存。
- **方案**：
  - 新增云集合 `schedule`，一条覆盖一个文档：`{ weekTag, week, slot, classId, timestamp }`。
  - **跨周失效靠分区，不靠删除**：`weekTag` = 该周周一的日期（`mondayTag()`）。读取只查 `weekTag === 本周一`，上周的文档天然匹配不到。无需删除操作、无需定时任务。
  - **追加式写入 + 同键取最新**：改调课不改旧文档，而是新增一条；解析时同一「星期-节次」由 `timestamp` 最新者胜出。
  - 读写封装在 `miniprogram/utils/scheduleStore.js`，供课表页与打卡页（智能推荐）共用。
- **为什么选追加式而不是更新覆盖**：云库预设权限「仅创建者可读写」下，**只能改自己创建的文档**。若用更新，她建的调课你就改不了。靠"后写的胜出"，双方都能改对方的调课，且**不依赖 D009 落地**。代价是同一条调课改几次留几条文档，量极小。
- **为什么拒绝的方案**：按日期存（`"2026-10-15-4"`）语义更准，但会让智能推荐的"向后扫未来 7 天"必须改成按真实日期逐个匹配，改动与复杂度显著更大。
- **已知副作用（接受）**：
  1. 集合不存在或网络故障时，课表页与智能推荐**降级为按原始课表**（不白屏、不报错），仅 console 记录。
  2. 老设备本地缓存里的旧调课**不再被读取**（未主动删除，留着无害），需重新调一次。
  3. 云库预设权限下**任何微信用户都能新增 `schedule` 文档**（create 在预设下永远允许）。上线前应收敛，**D009 的白名单规则要同时应用到 `progress` 和 `schedule` 两个集合**。
- **已验证**：离线测试 19 项（`mondayTag` 周一边界含跨年、同周一致性、跨周自动失效、同键取最新、取消课、55 条分页取全、写入带本周 tag）全部通过；用户已建集合并验收通过（2026-09-23）。

## D016 — 修复旧数据回补的分页 bug（limit 上限 20）

- **日期**：2026-09-23
- **背景**：核对小程序端查询限制时发现 `fixLegacyTotalPages()`（T2.4 旧数据回补）用 `pageSize = 100` 作为 `skip`/`limit` 的步长，但**小程序端单次查询最多返回 20 条** —— 每页只拿回 20 条，循环却按 100 步进，导致第 20 条之后的记录**整段被跳过，从未被回补**。且 `legacyPagesFixed` 标记已写入 storage，回补永远不会再跑。
- **方案**：
  1. `pageSize` 100 → **20**，与 limit 严格一致。
  2. 补 `.orderBy('_id', 'asc')` —— 不带显式排序时 `skip`/`limit` 的分页顺序不保证稳定，可能漏读或重读。
  3. 存储键 `legacyPagesFixed` → **`legacyPagesFixed_v2`**，让修好的回补能在用户设备上自动重跑一次（回补逻辑本身幂等，只改 `partial` 且 `totalPage` 对不上的记录）。
- **为什么**：这是一条会静默丢失数据的 bug，不是风格问题。官方 limit 上限已写进 AGENTS.md §3 作为硬约束。
- **已验证**：离线测试造 23 条 `totalPage` 错误的记录，回补后 23 条全部修正（旧代码只会修前 20 条）；全项目分页点审计确认步长均等于 limit；用户开发者工具验收通过（2026-09-23）。
